# CalorieAI 官网规划与当前实现

本文件规划并记录 `calorieai.sxyq27.online` 官网的落地方式。官网与现有更新服务复用同一个容器，不新增常驻进程。

官网静态源已落在 `deploy/calorieai-gateway/web/`，包含 `index.html`、`assets/site.css`、`assets/site.js` 和本地 Logo。站点采用 Stitch 项目 `18037500192872421969` 的 `CalorieAI Neo-Academic Editorial` 设计系统，并保留六个单页视图：功能概览、App 展示、下载应用、更新记录、帮助文档、隐私与安全。

2026-09-06 二轮逻辑修复：① `apkUrl` 校验兼容完整地址与 `/releases/...` 相对路径；正式站允许固定的 101 IP 直连更新地址，其余非 HTTPS 地址仍拒绝；② 预设文案修正为「GPT-5.6 Luna」，明确预设不内置密钥、需先填 API Key 才能启用，删除"零配置/开箱即用"表述；③ 隐私说明区分自定义直连地址与默认中转服务 `oneapi.sxyq27.online`；④ 清单请求加 10 秒超时（AbortController）；⑤ 下载前用 HEAD 预检通道，429/HTTP 错误/超时/断网均有页面内提示，确认后用隐藏锚点触发下载不跳页；⑥ 包体大小改为 `data-apk-size` 动态占位，清单到达后全站统一替换；⑦ `?manifest=` 覆盖仅限 localhost 自测；⑧ 移除无效变量，弹窗补焦点圈与焦点归还、FAQ 补 aria-expanded。每日调用限制经代码核实为每条配置 50 次/天（`AIChatUiState` 中的 10 为 UI 初始占位），官网文案与此一致。

## 当前已确认的服务现状

以下为 2026-09-02 在 124 服务器上的实时检查结果，不是历史记录。

| 项目 | 实测值 | 对官网的约束 |
| --- | --- | --- |
| CPU | 4 核 | 静态站无压力 |
| 内存 | 3.6 Gi 总量，已用 48%，可用 1.9 Gi | 不能新增数据库或 Node 常驻 |
| 磁盘 | 40 Gi 总量，可用 15 Gi | 不能放大量图片或视频 |
| 更新容器 | `calorieai-gateway`，4.76 MiB / 128 MiB，健康 | 复用它承载官网 |
| 官网根目录 | `/srv/calorieai-web`，当前为空 | 静态文件放这里 |
| APK 占用 | 两个版本共 726 MiB | 磁盘余量是硬约束 |
| 域名证书 | Let's Encrypt，有效期至 2026-11-29 | 已覆盖官网，无需再申请 |
| 并发下载限制 | 已生效，第二个下载返回 429 | 官网不得绕过该限制 |

关键判断：容器里已经把 `/srv/calorieai-web` 挂成 web 根目录，且 `location /` 的 `try_files` 已经把请求转到这里。实测访问根路径返回 404，说明请求确实进了容器、只是目录还空着。**官网不需要新建容器、不需要新端口、不需要新证书。**

## 为什么是纯静态站

这是由服务器余量决定的，不是偏好。

1. 内存只剩 1.9 Gi 可用，且 MySQL 已占 370 MiB。再加一个数据库或 Node 进程会挤掉 AstrBot、NapCat 和监控服务。
2. 磁盘可用 15 Gi，其中 726 MiB 已经被两个 APK 占住。官网不能引入大体积素材。
3. 现有容器限制为 128 MiB 内存、0.5 核。静态站正好落在这个额度内。
4. APK 下载限流是全局单并发，官网静态资源走的是另一条 `location`，不争抢下载额度。

因此官网定为一个纯静态站点：HTML + CSS + 少量 JS，无后端、无数据库、无构建流水线常驻。

## 站点结构

```text
/srv/calorieai-web/
├── index.html              # 首页：功能介绍 + 下载入口
├── download.html           # 下载页：版本说明 + 校验值
├── privacy.html            # 隐私说明
├── assets/
│   ├── css/site.css
│   ├── img/                # 截图与图标，总量控制在 5 MiB 内
│   └── js/download.js      # 读取 latest.json 渲染版本与大小
└── favicon.ico
```

官网的下载按钮不写死版本号，而是从 `/android/stable/latest.json` 读取。这样发布新版本时官网不用改。

## 页面内容规划

### 首页

首页要一眼说清这是什么、给谁用、怎么拿到。按现有 README 的真实功能组织，不编造未实现的能力。

- 首屏：产品名 + 一句话定位（本地优先的 Android 热量记录应用）+ 主下载按钮 + 当前版本号
- 功能区：按 APP 实际模块分四组
  - 食物记录：文本描述、拍照识别、手动录入、13 项营养指标
  - AI 助手：8 种服务商协议（OpenAI、Claude、Kimi、GLM、Qwen、DeepSeek、Gemini、LongCat）、流式响应、本地保存配置
  - 健康追踪：饮食、运动、体重、饮水与目标管理
  - 数据管理：Room 本地存储、JSON 备份、WebDAV 云备份、覆盖与合并两种恢复
- 隐私区：强调数据留在本地、AI 密钥本地加密
- 底部：系统要求（Android 8.0 及以上）、APK 大小提示、校验值入口

### 下载页

- 当前版本名与 versionCode，从 `latest.json` 读取
- APK 实际大小，按字节换算成 MB 展示
- SHA-256 完整值，供用户自行校验
- 更新说明，直接取 `releaseNotes`
- 下载按钮指向 `apkUrl`
- 提示：同时只允许一个下载，遇到"下载繁忙"稍后重试

### 隐私页

需要如实说明三点，这与代码实现一致：

- 健康数据存在本机 Room 数据库，不上传服务器
- AI 密钥经本地加密保存，源码不含内置密钥
- 备份由用户主动触发，WebDAV 地址与凭据由用户自己提供

## 与更新服务的边界

官网继续使用 124 的 HTTPS 域名入口，APK 下载改走 101 的 IP 入口，清单由官网入口展示但内容需与 101 发布版本同步。

首屏保留现有产品说明与结构化手机预览，并加入轻量字符背景层：字符密度由低频噪声生成，指针经过首屏时在附近提亮并显示柔和余辉；首屏离开后恢复低对比度。效果使用 `requestAnimationFrame`、可见区域监听和 `prefers-reduced-motion` 降级，不参与内容布局，也不影响下载与版本清单逻辑。

| 路径 | 用途 | 缓存 | 限流 |
| --- | --- | --- | --- |
| `/` | 官网首页 | 短缓存 | 不限 |
| `/assets/**` | 静态资源 | 长缓存 | 不限 |
| `/android/stable/latest.json` | 版本清单（官网经 124 展示，源文件同步到 101） | no-store | 不限 |
| `/releases/**/*.apk` | APK 下载（101:80 直连） | 长期缓存 | 单并发，超出返回 429 |
| `/healthz` | 健康检查 | no-store | 不限 |

`latest.json` 设为 `no-store` 是必须的，否则用户会拿到缓存的旧版本号，导致更新提醒失效。

## 视觉风格

官网应与 APP 保持一致，而不是另做一套。APP 用的是 Material 3、毛玻璃卡片和深色为主的配色。官网沿用同一套：深色背景、卡片圆角 8px、强调色与 APP 主色一致。

截图必须来自真实 APP 界面，不用素材网站的图。截图在 `assets/img/` 下按页面命名，单张压缩到 200 KiB 以内，总量控制在 5 MiB。

## 风险与待确认

- 磁盘余量 15 Gi。官网素材加两个 APK 后仍有余量，但如果以后要保留更多 APK 版本，需要先扩盘或改对象存储。
- 证书 2026-11-29 到期。官网与更新服务共用同一张证书，续期失败会同时影响两边。
- 官网截图需从真实 APP 界面采集并压缩；当前界面展示区使用结构化 CSS 预览代替，页面已预留截图位（见 `#view-showcase` 尾注）。
- 当前 APK 约 363 MiB，主要来自内置的 SenseVoice 语音模型。官网已在首页、下载页与 FAQ 三处明确提示安装包体积。
- `nginx.conf` 原先 `location = /` 返回 404，已于 2026-09-06 移除该块；部署时需执行 `scripts/deploy_calorieai_gateway.sh prepare` 重建容器后，根路径方可返回官网。
